# Async Runtime Design (AnyIO Boundaries)

This page is the authoritative design for the DojoAgents async runtime: which modules may use
`asyncio`, who owns each asynchronous task, how timeouts and cancellation are expressed, and how
threads and buffers are bounded. All new production code must follow it.

The pre-migration `asyncio` usage was converged in stages. The reference matrix is generated by
`.agents/scripts/audit_asyncio_usage.py`, and the AST gate is enforced by
`tests/test_asyncio_boundaries.py`.

## 1. AnyIO Architectural Boundaries

Three layers with one-way dependencies:

| Layer | Module | Responsibility |
| --- | --- | --- |
| Business | `dojoagents/{agent,gateway,dashboard,tools,multi_agent,planning,memory,...}` | AnyIO primitives only; `import asyncio` is FORBIDDEN |
| Primitives | `dojoagents/utils/async_runtime.py` | Bounded sync offload, order-preserving concurrency, timeout wrappers, cancellation detection |
| Bridge | `dojoagents/utils/blocking_portal.py` | The only supported channel between sync threads and the event loop |

The primitives layer exposes exactly four capabilities:

- `run_sync_bounded(function, /, *args, workload=..., limiter=..., abandon_on_cancel=False, **kwargs)`
  — offloads blocking calls to a bounded thread pool. Keyword arguments are bound with
  `functools.partial` because AnyIO's `run_sync` forwards positional arguments only.
- `gather_ordered(operations, *, max_concurrency=None, return_exceptions=False)`
  — runs operations concurrently and **preserves input order**. A child failure stays in its own
  slot, siblings still finish, and the first error in input order is re-raised. An
  `ExceptionGroup` is **never** leaked to the caller.
- `operation_timeout(timeout_seconds, *, operation=...)`
  — converts only the deadline this scope itself triggered into `OperationTimeoutError`; a
  `TimeoutError` raised by the wrapped code passes through unchanged.
- `is_cancelled_exception(exc)` — equivalent to
  `isinstance(exc, anyio.get_cancelled_exc_class())`; must be called from async context.

Workload tiers and capacities (`dojoagents/utils/async_runtime.py`):

| Tier | Capacity | Use |
| --- | --- | --- |
| `SyncWorkload.FILE_IO` | `FILE_IO_LIMIT = 16` | Local files, JSON/JSONL I/O |
| `SyncWorkload.SDK_IO` | `SDK_IO_LIMIT = 8` | DojoSDK and external data-source calls |
| `SyncWorkload.CPU` | `CPU_WORK_LIMIT = 4` | Pure computation (pandas/polars assembly, indicators) |

Capacities live in AnyIO `RunVar` values (isolated per async context) rather than in limiters
constructed at import time, so tests cannot pollute each other and the module stays backend-safe.

## 2. TaskGroup Ownership

**Every background task must have a TaskGroup owner whose lifetime encloses it.** Free-floating
tasks are not allowed.

| Host | Owner | Location |
| --- | --- | --- |
| Dashboard application | `service_tasks` (task group inside the lifespan) | `dashboard/server.py` |
| One Dashboard chat SSE response | lifespan `service_tasks` plus a per-request `OwnedSSEProducer` cancel scope | `dashboard/server.py` / `dashboard/sse.py` |
| Persisted run event replay stream | lifespan `service_tasks` plus a per-request `OwnedSSEProducer` cancel scope | `dashboard/server.py` / `dashboard/sse.py` |
| Dashboard background agent run | the portal loop owned by `AgentRunManager` | `dashboard/agent_runs.py` |
| Agent event fan-out | `dojo-events:<run_id>` task of `AgentEventBus` | `agent/session_run.py` |
| Agent heartbeat | `dojo-heartbeat:<run_id>` | `agent/session_run.py` |
| Provider streaming chat | `dojo-provider-chat` | `agent/loop.py` |
| Gateway service | task group in `gateway/server.py` | `gateway/server.py` |
| Gateway runner long-lived tasks | `GatewayRunner._owned_task_group` | `gateway/runner.py` |
| Gateway stream consumption | `stream_consumer._run_owned` | `gateway/stream_consumer.py` |
| MCP server supervisor loop | `server_tasks` (one per session cycle) | `tools/mcp_tool.py` |
| Multi-agent team | `AgentTeam._task_group` | `multi_agent/team.py` |
| Subprocess drain/reap | `dojoagents/utils/detached_tasks.py` (the single exception, see §9) | `tools/process_registry.py` |

Rules:

- **Bare `asyncio.create_task()` is FORBIDDEN.** `create_task` may appear only inside
  `detached_tasks.py`.
- A TaskGroup's `__aenter__`/`__aexit__` must run in the **same task at the same depth**.
  Entering a task group in one task and exiting it in another raises
  `RuntimeError: Attempted to exit a cancel scope that isn't the current tasks's current cancel scope`.
  Long-lived components such as `GatewayRunner` hold it by keeping their host task alive; short-lived
  tasks must not copy that pattern.
- When a component needs a task to outlive the request that created it, the correct solution is to
  give the **component** a dedicated portal event loop (§3) instead of detaching the task from
  structured concurrency.

## 3. Service Startup and Shutdown

### 3.1 The cross-thread bridge: `ThreadedBlockingPortal`

`dojoagents/utils/blocking_portal.py` wraps `anyio.from_thread.start_blocking_portal` in an
explicit, idempotent lifecycle object so sync threads (CLI, signal handlers, plugin registration)
can drive asynchronous components:

```
start() -> ready -> accept sync-thread calls -> shutdown() stops accepting -> close portal -> thread exits
```

- `start()` and `shutdown()` are both idempotent; repeated calls never produce a second event-loop
  thread.
- `shutdown()` **switches state to `closing` and clears the portal reference first**, before touching
  the loop. Late callers during shutdown therefore always receive `PortalClosedError` (an
  explainable error) instead of hanging.
- `portal.call(portal.stop, cancel_remaining=True)` already makes `start_blocking_portal` perform its
  own `thread.join()`; an implementation must **not** join by hand.
- Call constraints: `call()`, `start_task()`, and `call_async()` all refuse to run on the portal's
  **own event-loop thread** (`PortalThreadError`), which would otherwise be a guaranteed deadlock.
- `call_async()` consumes a worker thread (AnyIO has no thread-free way to await a foreign loop), so
  it uses a portal-private `CapacityLimiter(bridge_concurrency=8)` and cannot starve the project's
  file/SDK worker pools.
- `run_sync()` is the sole async entry point for cross-loop future cancellation, settlement waits,
  and synchronous shutdown. It reuses the same portal-private limiter and delegates to
  `run_sync_bounded()`; business modules must not call `anyio.to_thread.run_sync()` directly.
- Timeout semantics: a `call()` overrun raises `PortalCallTimeout`. Cancellation is issued from a
  **background daemon thread** — `concurrent.futures.Future.cancel()` runs its done callbacks inline,
  and the portal's callback has to hand cancellation back to the portal loop, so calling it on the
  timed-out caller's thread would **re-block** that thread.
- By the same token, calling `future.cancel()` **from the event-loop thread** dies in
  `call_soon_threadsafe`; cancellation and waiting therefore always go through
  `await portal.run_sync(future.cancel, abandon_on_cancel=True)`.
- There is no `__del__`; asynchronous cleanup never depends on the garbage collector.

Defaults: `DEFAULT_CALL_TIMEOUT_SECONDS = 120`, `DEFAULT_SHUTDOWN_TIMEOUT_SECONDS = 10`.

### 3.2 Component startup and shutdown order

| Component | Startup | Shutdown |
| --- | --- | --- |
| Dashboard | `lifespan` creates `service_tasks`; `DashboardAppServices.startup(task_group=...)` | `service_tasks.cancel_scope.cancel()` then a cancellation-shielded teardown sequence |
| Dashboard financial services | `app_container.startup()` runs inside `async with anyio.from_thread.BlockingPortal()` | `app_container.shutdown()` |
| Dashboard background runs | `AgentRunManager.__init__` creates and starts its own portal | `AgentRunManager.shutdown()`: cancel every run and wait for `settled`, then `portal.shutdown()` |
| MCP | `MCPToolRuntime.start_server()`: start portal, start the `serve()` supervisor, poll `ready` | `MCPToolRuntime.shutdown()`: stop every server, clear the registry, `portal.shutdown()` |
| Gateway | the task group in `gateway/server.py` | same; exiting the group converges everything |

**The teardown sequence must be wrapped entirely in `with anyio.CancelScope(shield=True):`**
(see `dashboard/server.py`). Reason: `service_tasks.cancel_scope.cancel()` leaves the **current task
itself** cancellation-pending, so every checkpoint outside a shield — including `anyio.sleep(0)` and
`to_thread.run_sync(..., abandon_on_cancel=True)` — raises `CancelledError` immediately and the
teardown never completes. Teardown is a bounded, best-effort sequence and must run to the end.

**The inverse hard rule**: any `__exit__`/`__aexit__` that **closes a cancel scope** must **not** be
wrapped in `CancelScope(shield=True)` or `move_on_after`, or it raises
`RuntimeError: Attempted to exit a cancel scope that isn't the current tasks's current cancel scope`.
Only a task-group `__aexit__` that contains an awaited checkpoint violates this. Shutdown
boundedness therefore comes from **the closing function's own timeout parameter**
(`shutdown(timeout=...)`, `MCP_*_TIMEOUT_SECONDS`), never from scope wrapping.

### 3.3 What is allowed during cancellation

Once a task is cancellation-pending, only awaits **inside a shield** execute. Cleanup that must log or
persist has to look like this:

```python
finally:
    with anyio.CancelScope(shield=True):
        LOGGER.warning("run cancelled; persisting final state")
        await anyio.to_thread.run_sync(write_final_state)
```

An unshielded `await` raises `CancelledError` at its first checkpoint, and the synchronous statements
after it never run.

## 4. Timeout and Cancellation Rules

### 4.1 Timeouts

- Use `anyio.fail_after(seconds)` for hard deadlines; it converts `CancelledError` into
  `TimeoutError`. **The cancellation stays inside that scope and does not leak to the caller.**
- Use `anyio.move_on_after(seconds)` when the timeout must continue down the normal path, then check
  `scope.cancelled_caught` — for example "flush once when the polling window elapses".
- When the timeout must be distinguished from a `TimeoutError` already raised by inner code, use
  `async_runtime.operation_timeout()`.
- Every timeout must be a **named constant or config value**; scattered literals are not allowed.
  Current conventions:

| Component | Constant | Default |
| --- | --- | --- |
| Tool execution | `sandbox.timeout_seconds` | from SandboxPolicy |
| Portal call / shutdown | `DEFAULT_CALL_TIMEOUT_SECONDS` / `DEFAULT_SHUTDOWN_TIMEOUT_SECONDS` | 120 / 10 |
| MCP connect / start / stop / call / shutdown | `MCP_CONNECT_` / `MCP_START_` / `MCP_STOP_` / `MCP_CALL_` / `MCP_SHUTDOWN_TIMEOUT_SECONDS` | 15 / 30 / 10 / 120 / 30 |
| MCP keepalive | `MCP_KEEPALIVE_INTERVAL_SECONDS` / `MCP_KEEPALIVE_TIMEOUT_SECONDS` | 180 / 30 |
| MCP reconnect backoff | `MCP_RECONNECT_BACKOFF_SECONDS` / `MCP_RECONNECT_MAX_BACKOFF_SECONDS` | 1.0 / 30.0 |
| Subprocess terminate grace | `DEFAULT_TERMINATE_GRACE_SECONDS` | 5.0 |
| Subprocess single-line cap | `DEFAULT_MAX_LINE_BYTES` | 4 MiB |
| Waiting for a run to settle after cancel | `_RUN_CANCEL_SETTLE_SECONDS` | 10.0 |

MCP reconnection must **back off before reconnecting** and the backoff must be capped
(`min(1.0 * 2 ** (n-1), 30.0)`); otherwise it becomes an unthrottled hot reconnect loop.

### 4.2 Cancellation

- Always detect cancellation with `anyio.get_cancelled_exc_class()`; never write
  `asyncio.CancelledError`. On the asyncio backend it is not an `Exception` subclass, which is exactly
  the behaviour we want.
- **Never swallow cancellation with `except Exception`.** A cleanup branch that catches `Exception`
  must re-raise the cancellation, or split it out at the boundary with `BaseExceptionGroup.split()`:

```python
except BaseExceptionGroup as exc:
    cancelled, remainder = exc.split(anyio.get_cancelled_exc_class())
    if cancelled is not None:
        raise cancelled
    # remainder holds the real business errors
```

- **Public APIs never leak `ExceptionGroup`.** Tool and route boundaries split the group, re-raise
  cancellation, and convert business errors into `ToolResult(ok=False, error=...)` or HTTP errors.
  `gather_ordered` already guarantees this.
- Repeated cancellation must be idempotent: `CancelScope.cancel()` may be called repeatedly, and a
  `Future` / task whose scope already exited must not be cancelled again. Cancellation converges on
  "wait for `settled`, then best-effort set the terminal status on timeout" — see
  `AgentRunManager.cancel_run()`.
- Logging and persistence must still happen during cancellation — see the shielded pattern in §3.3.

## 5. Thread Limiters

- All blocking I/O must go through `run_sync_bounded(...)` onto a bounded thread pool. Bare
  `anyio.to_thread.run_sync()` and self-built `ThreadPoolExecutor` instances are **not allowed**:
  they fall back to AnyIO's shared 40-thread default and cannot be isolated per workload.
- Pick the right `workload` tier; do not funnel all blocking work into `FILE_IO`.
- `abandon_on_cancel` defaults to `False`: write-like operations must wait for the worker instead of
  being abandoned midway. Only reads whose result may be discarded use `abandon_on_cancel=True`.
- Independent throttling may pass an explicit `limiter=` (for example the portal's own bridge
  limiter), but it must be a bounded object.
- Portal lifecycle bridges use `ThreadedBlockingPortal.run_sync()`, whose private bounded limiter
  keeps this work separate from file-I/O and SDK-I/O capacity.
- Acceptance check: submit `2 × FILE_IO_LIMIT` blocking tasks and measure a peak concurrency exactly
  equal to `FILE_IO_LIMIT`. See `tests/test_resource_bounds.py`.

## 6. Memory Stream Capacity Rules

`anyio.create_memory_object_stream()` **must be given an explicit finite `max_buffer_size`**.
`math.inf`, `float("inf")`, and omitting the argument are forbidden — the gate test
`test_memory_object_streams_have_explicit_finite_buffers` fails on them.

Current registry (changes must update this table):

| Location | Capacity | Consumer |
| --- | --- | --- |
| `agent/loop.py` | 64 | provider deltas → agent events |
| `agent/session_run.py` | 32 | event fan-out to the session log |
| `gateway/stream_consumer.py` | 64 | editor streaming flush |
| `dashboard/sse.py` (`SSE_EVENT_BUFFER_SIZE`) | 32 | SSE event push |
| `dashboard/server.py` (chat SSE) | 32 | SSE event push |
| `dashboard/server.py` (persisted run replay) | 1 | event replay |
| `tools/process_registry.py` | 32 | background process completion notices |

Backpressure conventions:

- Producers use `send_nowait()` inside the loop. When the buffer is full they must fail within a
  **bounded** time rather than waiting indefinitely: `dashboard/sse.py` raises
  `StreamBackpressureError`, other sites raise a `RuntimeError` whose message includes
  `(capacity=N)`. That capacity text must match the real `max_buffer_size`.
- Closing the sender is the termination signal. Consumers rely on `anyio.EndOfStream` /
  `ClosedResourceError`; `receive()` **raises** at EOF rather than returning an empty value.
- Cross-thread delivery is covered by §7. Do not add unbounded capacity to a stream.

## 7. SSE Cross-Thread Bridging

SSE events originate from agent callbacks that may run on worker threads, while the memory stream is
bound to the event loop, so delivery must go through a `BlockingPortal`.

- `dashboard/sse.py::SSEEventStream` holds `send_stream` / `receive_stream` (capacity 32) and an
  optional `_portal`.
- The app-owned producer calls `bind_portal(portal)` / `unbind_portal()` as a pair inside
  `async with`. Same-thread callbacks use `send_nowait()`; external-thread callbacks use
  `portal.call(send)`. **Late or already-closed callbacks are dropped silently.**
- The portal is created **inside the event loop**
  (`async with anyio.from_thread.BlockingPortal() as portal:`). It starts no thread and no loop, its
  scope is the producer, and `unbind_portal()` runs in `finally`. This is not the same as "hand-rolling
  an event-loop thread per request", but it is a literal exception to the "do not create a portal per
  request" rule, so it is recorded here to avoid being misread as a violation.
- Producers are owned by the lifespan's `service_tasks`. `OwnedSSEProducer` enters and exits each
  request's cancel scope inside the producer task. A response generator only drains the receive
  stream and never holds a TaskGroup, BlockingPortal, or CancelScope across `yield`. On disconnect it
  calls `producer.stop()` and waits a bounded time for cleanup.
- Sender shutdown uses `with anyio.CancelScope(shield=True): await event_stream.close()`; persisted
  replay iterators are likewise closed by their producer in the same task.
- The Gateway uses the same pattern: `gateway/stream_consumer.py` creates the portal inside the loop
  and owns the producer via `task_group.start_soon(self._run_owned)`.

## 8. Subprocess Reclamation

The unified process adapter lives in `dojoagents/tools/processes.py` (`Process`, `open_process()`,
`run_process()`, `ProcessResult`, `terminate_then_kill()`, plus the re-exported
`PIPE` / `DEVNULL` / `STDOUT` / `INHERIT`). Business code must **not** use
`asyncio.create_subprocess_*` or `anyio.open_process()` directly.

- The process returned by `anyio.open_process()` (and by this adapter's `open_process()`) is
  **detached**: exiting or cancelling the enclosing scope does **not** kill it, so it must be
  reclaimed explicitly.
- `run_process()` is for short commands; AnyIO reaps the child when the caller is cancelled.
- Always reclaim with `terminate_then_kill(process, *, grace_seconds=5.0)`:
  `SIGTERM → grace → SIGKILL → wait()`, entirely inside `anyio.CancelScope(shield=True)`. It is
  therefore safe to call from a `finally` block, a timeout handler, or a cancellation handler, and it
  guarantees the child is reaped. Calling it on an already-exited process is idempotent.
- Draining stdout and reaping a *long-lived* child must outlive the tool call that spawned it → use
  `dojoagents/utils/detached_tasks.py` (the single exception in §9), together with
  `process_registry`'s dynamic pruning and its reaper holding the session object directly.
- Long-lived processes use `INHERIT` for `stdin/stdout/stderr` (= `None`, i.e. inherited) so logs stay
  visible; switching to `PIPE` hides the logs and can fill the pipe and stall the child.
- `Process.communicate()` is implemented in this layer (AnyIO byte streams have no `communicate()`).
- `DEFAULT_MAX_LINE_BYTES = 4 MiB` bounds single-line reads so newline-free output cannot exhaust
  memory.

## 9. asyncio Compatibility Allowlist

Production code may `import asyncio` in exactly two files, both registered in
`tests/test_asyncio_boundaries.py::PERMANENT_ASYNCIO_ALLOWLIST` and
`.agents/scripts/audit_asyncio_usage.py::PRESERVE_ALLOWLIST`:

| File | Reason | Removal condition |
| --- | --- | --- |
| `dojoagents/tools/af_unix_asyncio_compat.py` | AnyIO offers no high-level AF_UNIX helpers; this module also adds AF_UNIX support under the Windows Proactor loop | Delete entirely once AnyIO exposes equivalent AF_UNIX connection/server primitives |
| `dojoagents/utils/detached_tasks.py` | AnyIO is a structured-concurrency library and has **no** fire-and-forget primitive, yet background-process drain/reap must outlive the call that started it | Delete entirely once AnyIO exposes a public, scope-safe detached-task primitive |

`TEMPORARY_ASYNCIO_ALLOWLIST` is empty and must stay empty — it is the migration ratchet. Any new
`asyncio` import fails `test_asyncio_imports_are_confined_to_registered_boundaries`.

Outside that allowlist, new production code must use AnyIO and must **not** add `asyncio` imports, bare
background tasks, or unbounded async queues. Test files are not yet subject to the production
zero-reference requirement.

Retention conditions (a new allowlist entry must satisfy every one):

1. A third-party library explicitly requires asyncio, or AnyIO is confirmed to have no equivalent
   primitive (with probe evidence);
2. the code is compressed into a very thin adapter;
3. the adapter contains no business logic;
4. asyncio types do not leak into the public interface;
5. the top of the file states the reason and the removal condition;
6. it is registered in the AST allowlist test.

Known deviations: `detached_tasks.py` does not satisfy condition 1 in its "third-party library"
wording (it is an AnyIO primitive gap, and three probe results are recorded at the top of the file),
and `start_detached()` used to return `asyncio.Task` (condition 4); it no longer exposes an asyncio
type.

## 10. New Service Template

When adding a service that needs background tasks or a sync bridge, follow this skeleton:

```python
from __future__ import annotations

import anyio
from dojoagents.logging import LOGGER
from dojoagents.utils.async_runtime import SyncWorkload, run_sync_bounded

# 1) Every timeout and capacity is a named constant
START_TIMEOUT_SECONDS = 30.0
STOP_TIMEOUT_SECONDS = 10.0
EVENT_BUFFER_SIZE = 32


class MyService:
    """Background service: tasks owned by a TaskGroup, closed by an explicit method."""

    def __init__(self) -> None:
        self._started = False
        self._closed = False

    async def startup(self, *, task_group: anyio.abc.TaskGroup | None = None) -> None:
        if self._started:
            return                                   # idempotent
        self._started = True
        with anyio.fail_after(START_TIMEOUT_SECONDS):
            await self._connect()
        # 2) Every background task needs an owner.
        #    Prefer borrowing the caller's task group (the FastAPI lifespan passes its own;
        #    that group's __aenter__/__aexit__ are both performed by the long-lived
        #    lifespan task).
        if task_group is None:
            # Self-creating a group and calling __aenter__ here works only when this
            # service's startup and shutdown are called by the *same long-lived task*:
            # the cancel scope binds to the current task, and exiting it from another
            # task raises
            # RuntimeError: Attempted to exit a cancel scope that isn't the current
            # tasks's current cancel scope.
            raise RuntimeError(
                "MyService needs a host task group; pass the owner's group or give "
                "this service a dedicated long-lived task / ThreadedBlockingPortal"
            )
        task_group.start_soon(self._run, name="dojo-my-service")

    async def _run(self) -> None:
        while True:
            await anyio.sleep(0)                     # structured loop; cancelled with the owner

    async def shutdown(self, *, timeout: float = STOP_TIMEOUT_SECONDS) -> None:
        if self._closed:
            return                                   # idempotent
        self._closed = True
        # 3) Teardown must be bounded: use the closing function's own timeout, never
        #    wrap somebody else's __aexit__ in a cancel scope.
        with anyio.move_on_after(timeout):
            await self._close_quietly()

    async def _close_quietly(self) -> None:
        try:
            with anyio.CancelScope(shield=True):     # 4) cleanup cannot be interrupted
                await self._disconnect()
        except Exception:                            # noqa: BLE001 - cleanup is best effort
            LOGGER.exception("MyService cleanup failed")

    async def _blocking_read(self, path: str) -> bytes:
        # 5) Blocking I/O goes through a bounded limiter
        def _read() -> bytes:
            with open(path, "rb") as handle:
                return handle.read()

        return await run_sync_bounded(_read, workload=SyncWorkload.FILE_IO)
```

Template rules: idempotent `startup`/`shutdown`; named timeouts; every background task has an owner
and **prefers borrowing the host task group**; cleanup runs under a shield; blocking I/O goes through
`run_sync_bounded`; cross-thread delivery uses `ThreadedBlockingPortal`; cancellation is detected with
`anyio.get_cancelled_exc_class()`; public methods never return an `ExceptionGroup`.
